520.3.2・User management & access control 34%

Access requests

使用者打開沒有權限的 app 時會被提示申請存取。這一節考你誰能申請什麼、在哪裡核准或拒絕、誰有權審，以及核准與拒絕各會帶來什麼後果。

考試佔 34%
官方考綱原文（這一節會考的範圍）
  • Manage product access for both non-managed and managed accounts管理 non-managed 與 managed 帳號的 app 存取（新版能力清單）
  • Understand when users request access了解使用者何時會申請存取（舊版 1.4）
  • Product access requests must be made by a user with a verified email address and Atlassian account申請者要有已驗證 email 與 Atlassian account（舊版 1.4）
  • You can approve or deny these requests on the Access requests page在 Access requests 頁核准或拒絕（舊版 1.4）
  • When you grant a user access to a product, they’re added to the default group for that product group (which may be the default group for other products, as well) and billing starts for the new user核准後使用者會被加進 default group（可能同時是其他 app 的 default group），並開始計費（舊版 1.4）
  • A user who has requested access and been denied won’t be able to request access again.被拒絕的人不能再申請（舊版 1.4）

3 分鐘速覽

使用者申請、admin 核准或拒絕

  1. 何時出現使用者打開沒有權限的 app（例如同事分享的連結），系統提示他申請存取。
  2. 誰能申請什麼已有某個 app 的人：替自己申請新的 app、或替別人申請自己已有的 app；新使用者：只能替自己申請。
  3. 申請條件要有 Atlassian account 與已驗證的 email；admin 不核准就進不來。
  4. 在哪裡審Centralized：Apps›User requests›Access requests，彙整所有 site；original：Apps → 選 site → Access requests。也可以從 email 審。
  5. 誰能審Org admin；site admin 只能審自己管的 site。User access admin 不能審。
  6. 拒絕被拒絕的人不能再申請；拒絕時可以附一段說明。
資料來源（4）有疑慮時點開看官方原文
  • Approve or deny app access requestsWhen a user lands in an app they don’t have access to, we prompt them to request access.
  • Approve or deny app access requestsUsers need an Atlassian account and a verified email address to request access to an app.
  • Approve or deny app access requestsAccess requests are collected into a list aggregated from all sites in your organization.
  • Approve or deny app access requestsWhen you deny access for a user, they can’t request access again. Send them a short message to explain why you denied their request.
何時

誰會送出申請、能申請什麼

使用者類型可以申請
已經有你們至少一個 app 的人替自己申請新的 app；替別人申請「自己已經有的那個 app」
新使用者（還沒有任何 app）只能替自己申請
  • 常見觸發點：沒有存取的人打開同事分享的 Jira 或 Confluence 連結。
  • 和 520.3.1 的設定連動：User invites 選 Require admin approval 時，使用者不能直接邀請，改成送出申請；approved domain 或 Any domain 勾了 Required 時，該網域的人也要經過核准。選 Don't allow invites 則連申請都不行。
  • 申請者一定要有 Atlassian account，而且 email 已驗證。

所以「誰會出現在 Access requests 清單」取決於 app access settings。考題若問「為什麼看不到某人的申請」，先想他是不是被設定成不能申請，或 email 還沒驗證。

本段必考
  • 已有 app 的人可替別人申請「同一個 app」。
  • Require admin approval、Required 勾選都會讓請求進入 Access requests。
資料來源（4）有疑慮時點開看官方原文
  • Approve or deny app access requestsThis can happen when a user without access opens an app link shared by someone who has access.
  • Approve or deny app access requestsAccess for someone else to the same app they have access to.
  • Approve or deny app access requestsUsers can only access your site or apps if you choose to approve them.
  • Control how users get access to appsUsers can’t invite anyone to your product, but they can request access to your product for themselves or on behalf of someone else.
審核

核准、拒絕的位置與角色

CentralizedOriginal
路徑Apps → User requests → Access requestsApps → 側欄選 site → Access requests
按鈕Review → Approve；或 ••• → Deny accessReview request → Approve now；或 ••• → Deny access
清單範圍彙整 organization 內所有 site依 site 分開
誰能審Org admin；site admin（只限自己的 site）Org admin；site admin（只限自己的 site）
Site admin 核准之後收不回來（centralized）

Centralized 介面下，site admin 可以核准申請，但不能修改使用者；核准之後若要移除這個人，要找 org admin（或該 app 的 user access admin）。

本段必考
  • Org admin 與 site admin（限自己的 site）能審；user access admin 不在名單上。
  • Centralized 的清單彙整所有 site。
資料來源（6）有疑慮時點開看官方原文

  • Approve or deny app access requestsYou can approve or deny these requests in Atlassian Administration or through related emails.
  • Approve or deny app access requestsSelect Approve now to approve a request, or select more actions (•••) > Deny access to deny a request.
  • Approve or deny app access requestsThe other tab on the page, called User interests, is where you can keep track of and review trending user interest in new apps.

  • Site Administrator role in the Centralized user management and Original user management experiencesApprove or deny product access requests from existing users within the organization.
核准之後

Default group 與計費

  1. 核准＝給 app 存取使用者拿到申請的 app 角色，被放進該角色的 default group。
  2. 可能連帶其他 app如果這個 default group 也被設定成給其他 app 的存取，他會一起拿到其他 app（考綱：the default group … may be the default group for other products）。
  3. 開始計費有 User 角色就是計費使用者；就算還沒登入也會計入。
  4. 拒絕可以附一段簡短說明；被拒絕後他不能再送出申請。
考題長相

「核准申請後帳單人數增加、而且他還多了 Confluence」：他被放進 Jira 的 default group，而這個 group 也給了 Confluence。修正方式是調整 default group 的設定（見 520.3.4），不是撤銷申請。

本段必考
  • 核准→進 default group→開始計費。
  • 被拒絕的人不能再申請。
資料來源（3）・1 點無官方原文有疑慮時點開看官方原文
  • Give users access to appsWhen you give app access to a user, we add them to the default group for that app.
  • Give users access to appsIf the default group for an app has been modified to also give access to other apps, a user access admin for that app only won’t be able to give users access to that app.
  • Manage users and user tiersWhen users are added to an app, they’re automatically counted towards billing even if they don't accept your invite or log in.
  • 找不到官方原文：核准申請會進 default group 並開始計費這是舊版考綱 1.4 的原文；現行 Approve or deny app access requests 頁沒有逐字寫出，依 Give users access to apps 與 Manage users and user tiers 兩頁整理。

動手做

實作 Lab：Ana 申請 Jira，你來核准

約 20 分鐘Org admin；所有方案

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：從申請者與 admin 兩邊看一次 access request：Ana 送出申請、你核准、確認她被放進 default group。

這個 Lab 對應的考點

申請者要有 Atlassian account 與已驗證 email；centralized 下所有 site 的申請彙整在 Apps → User requests → Access requests；核准＝進 default group 並開始計費；被拒絕的人不能再申請。

準備

  • Ana 用她自己的 email（和你不同網域）先在 id.atlassian.com 建立 Atlassian account，並完成 email 驗證。
  • Ana 還沒有被邀請進 Lab Org。
  • App access settings 的 Any domain 維持預設（允許申請）。

步驟

  1. 你應該看到：Ana 沒有存取，畫面提示她申請存取。
  2. 你應該看到：畫面顯示申請已送出。
  3. 你應該看到：清單中有 Ana 的 Jira 申請；頁面另一個分頁是 User interests。
  4. 你應該看到：申請從待處理清單消失。
  5. 你應該看到：Ana 有 Jira 的 User 角色；Groups 裡有 jira-users-labjira 這類 Jira 的 default group。
  6. 你應該看到：Ana 進得了 Jira。
  7. 你應該看到：清單出現 Leo 的 Confluence 申請。先不要處理，看完 T1 再核准。

試試看：改一個設定，觀察差異

T1看 Leo 的申請畫面能不能替 Kim 申請 Confluence。看結果
通常不行：已有存取的人只能替別人申請「自己已經有的 app」。Leo 有 Jira、沒有 Confluence，所以只能替別人申請 Jira。
T2（想像，不實際做）對 Leo 的申請選 ••• → Deny access，並附上一段說明。看結果
Leo 收到說明，而且之後不能再申請 Confluence；要給他 Confluence 只能由 admin 主動給。所以 Lab 不要真的拒絕。
T3（想像，不實際做）Ana 的 Atlassian account 還沒驗證 email 就打開 Jira。看結果
她不能送出申請：申請者要有 Atlassian account 與已驗證的 email。
心像錨點：閉上眼睛想一次這個畫面

Access requests 清單：每列一個申請者與 app，右邊 Review、Approve，••• 裡藏著 Deny access。核准就進 default group、就計費；拒絕就不能再申請。

收尾

  • 核准 Leo 的 Confluence 申請（或在 Leo 的頁面直接 Grant access），讓之後的 Lab 可以用。
  • Ana 保留 Jira 存取，後面的 Lab 拿她當 external user 的例子。
