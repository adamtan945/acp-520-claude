3 分鐘速覽

Atlassian Guard（舊名 Atlassian Access）：organization 層級的安全訂閱

  1. Guard 是什麼Atlassian Guard（舊名 Atlassian Access）是替整個 organization 買的訂閱，提供使用者管理、身分驗證、資料保護與威脅偵測。
  2. Standard 與 PremiumGuard Standard 有 SAML SSO、user provisioning、user API token 管理、多個 authentication policy、external user 安全政策；Guard Premium 是加購，再加資料分類、敏感資料偵測、威脅偵測、延伸 audit log。
  3. 計費Guard Standard 依 organization 計費，每個有 app 存取的 managed account 或 external user 只算一次；Enterprise 方案已含 Guard Standard，不重複收費。
  4. Authentication policies依使用者分組設定 SSO、2SV、密碼、session、API token；每人同時只屬於一個 policy，最多 20 個 policy，成員來自 managed accounts。
  5. SSO 與 provisioningSAML SSO 只適用已驗證網域的帳號；user provisioning 用 SCIM 2.0，從 IdP 建立、更新、停用帳號並同步 group。
  6. API token 與 shadow ITInsights → API token activity 可看、可撤銷 managed account 的 API token；shadow IT 是使用者自己開的 app，Guard 會發 email 通知。

這張表最該記的：SSO、provisioning、多個 policy、external user 政策都是 Guard Standard；「偵測」與「分類」類的功能才是 Guard Premium。Guard Premium 是 Guard Standard 的加購，不能單獨買。

誰算 Guard Standard 的計費使用者

  • 是 managed account 或 external user，而且能存取 Jira、Confluence、Bitbucket、Trello、Jira Service Management 其中之一；只能存取 sandbox 的人也算。
  • 不論能用幾個 app、幾個 site，每人只算一次。
  • 不算：沒有 app 存取、帳號已停用、只用 JSM help center（customer）、只用 Jira Product Discovery、在 non-billable authentication policy 裡、方案已含 Guard Standard（例如 Enterprise）。
  • 要開始用 Guard Standard：要有 organization、驗證至少一個網域、再訂閱。開通位置是 Security → Start 30-day free trial。
考題長相

「Jira Standard 100 人，其中 50 人也用 Confluence Standard，Guard Standard 帳單算幾人？」答案是 100：每人只算一次。若 1,500 人用 Enterprise 的 Jira 與 Confluence、另有 50 人用 Bitbucket Standard，Guard 帳單是 50，因為 Enterprise 已含 Guard Standard。

本段必考
  • Standard：SSO、SCIM、API token、多 policy；Premium：偵測、分類。
  • 每人只算一次；Enterprise 已含 Guard Standard。

Authentication policies

依使用者分組設定登入規則

Authentication policy 決定一群 managed account 要怎麼登入。每個 organization 一開始就有一個 default policy；新 provision 的 managed account，或用 linked domain claim 進來的帳號，都會自動加進 default policy。要建立第二個以上的 policy，需要 Guard Standard。Policy 是針對使用者、不是針對 app；要給人 app 存取，仍然是另外指派 app 角色。

設定說明
Single sign-on（SAML 或 Google Workspace）Enforce single sign-on：成員必須透過 IdP 登入（Guard Standard）
Two-step verificationMandatory 或 Optional；啟用 SSO 後改在 IdP 設定
Third-party login允許或封鎖用 Google、Microsoft、Apple、Slack 帳號登入
Password requirements最低強度與到期天數；預設不會過期
Idle session duration／Session expiration閒置多久登出；固定多久一定要重新登入
User API tokens允許或封鎖建立、使用 API token；預設允許，更新最多 10 分鐘生效
API token expiration1～365 天或永不過期；預設建立後一年過期

這張表最該記的：一旦對某個 policy 啟用 SSO，2SV、密碼規則、third-party login 都改由 IdP 管，Atlassian 這邊的設定會被略過。

強制 SSO 前先留一條後路

對不在 IdP 裡的人強制 SSO，他們就無法登入。官方建議：先建一個測試 policy 只放少數帳號試 SSO；並準備一個用未驗證網域 email 的 org admin 帳號，放在不強制 SSO 的 policy，萬一設定錯了還能登入修正。

官方說法不一致：2SV 要不要 Guard

Enforce two-step verification 頁的「Who can do this」寫「All plans」，Authentication policy settings 頁的表格也把 2SV 的 Optional 列標為「Included by default」；但同頁的「Who can do this」寫套用 2SV 要 Guard Standard，Insights 頁也寫用 authentication policy 強制 2SV 要 Guard Standard。考題若問「哪個功能一定要 Guard」，選 SSO、user provisioning、多個 policy 這些沒有爭議的。

SSO 與 provisioning

把 identity provider 接到 organization

SAML single sign-on 讓使用者用公司 identity provider（IdP，例如 Okta、Microsoft Entra ID）登入一次，就能使用多個 Atlassian app。User provisioning 則是用 SCIM 2.0 從 IdP 自動建立、更新、停用帳號並同步 group。兩者都需要 Guard Standard，也都建立在已驗證的網域上。

SAML Just-in-timeSCIM user provisioning
何時建帳號使用者第一次用 SAML 登入時IdP 指派時就同步建立，不寄邀請信
條件網域已 link 到 IdP directory，且 default policy 強制 SAML SSOGuard Standard；IdP 支援 SCIM（或自己用 provisioning API 串）
停用帳號要在 organization 與 IdP 兩邊都停用只要在 IdP 停用
Group—IdP 推過來的 group 在 organization 是唯讀；default group 不能用 SCIM 管

這張表最該記的：連上 SCIM 之後，使用者屬性與 group 成員都改由 IdP 管；Atlassian 這邊不能改。IdP 推來的 group 若和 organization 既有 group 同名會報錯，和 site-admins、org-admins 這類內建 group 同名也無法同步。

考題長相

「Admin 想對外包人員（用 gmail.com）也套用 SAML SSO。」不行：SAML SSO 只適用你能驗證的網域。要管 external user 的登入，改用 external user policy（要求 SSO 或 one-time passcode）。

本段必考
  • SAML SSO 只適用已驗證網域的帳號。
  • SCIM 同步的 group 是唯讀，只能在 IdP 改。

API token 與 external users

撤銷 user API token、管住外部帳號

User API token 是使用者自己在帳號設定裡建立、用來跑 script 呼叫 app API 的憑證。Org admin 可以在 Insights → API token activity 集中看到所有 managed account 建立的 token：何時建立、何時到期、最後使用時間，並選一把或多把 Revoke。撤銷是永久刪除、無法復原。也可以從使用者頁的 Security 分頁撤銷單一 token。

你想要怎麼做
撤銷某人（managed account）的 tokenInsights → API token activity → Revoke；或使用者頁 → Security → API tokens
禁止某群 managed account 建立或使用 tokenAuthentication policy → Block members from creating a new or using an existing API token
讓 token 更快過期Authentication policy 的 API token expiration（1～365 天）
禁止所有 external user 用 token 呼叫 APIExternal user policy 的 API token access（套用到全部 external user）

External user policy

External user 是你沒有管理的帳號。Security → User security → External users 的 external user policy 套用到所有 external user：Authorization method 可選 single sign-on、one-time passcode（寄到 email 的一次性密碼）或 None；另外可設 session 到期、封鎖 email 內容預覽與行動通知、封鎖 API token。預設 external user 不需要再驗證身分就能存取。

官方說法不一致：看與撤銷 token 要不要 Guard

View API token activity 與 Revoke user API tokens 頁寫「Any plan」；但 Guard 方案表把 User API token management 列為 Guard Standard。作答時記住：撤銷 managed account 的 token 是 org admin 在 Insights 做的事；考綱稱這是 Atlassian Access 的能力。

本段必考
  • Insights → API token activity：看、撤銷 managed account 的 token，撤銷不可復原。
  • External user policy：SSO、one-time passcode 或 None，套用全部 external user。

Shadow IT 與 insights

使用者自己開的 app、organization 的使用分析

Shadow IT 指使用者自己註冊、自己管理的 Atlassian app。它們不在你的 organization 底下，所以 Atlassian Administration 的 Apps 頁找不到。風險有三：資料不在你的掌控中（使用者還可能加外部人進去）、帳單可能超出預期、事後整併要花工夫。

  • Discover shadow IT apps（Guard Standard）：你的 managed account 自己註冊 Atlassian app 時，你會收到 email，並可在 Shadow IT apps 畫面看到清單、匯出 CSV、聯絡該 app 的 admin。
  • 官方寫的是「managed account 自己註冊 app 時」才通知，所以要先驗證網域並 claim 帳號，這個功能才有對象（推論）。
  • Insights → Analytics：看哪些網域有 app 存取、managed account 與 external user 的人數、managed account 用 SSO 或 2SV 登入的比例、行動 app 使用、Jira 使用率等。部分圖表要 Guard Standard 或 Premium 方案，多數每 24 小時更新。
考題長相

「Admin 想知道員工自己用公司 email 開了哪些 Jira site。」答案是 Guard 的 Shadow IT apps（discovered apps），不是 Apps 頁，也不是 audit log。考綱用語是「Understand how Shadow IT sites are created」：使用者自己去註冊就會產生。

本段必考
  • Shadow IT＝使用者自己註冊的 app，不在 Apps 頁。
  • Insights → Analytics 看驗證方式、網域分布、使用率。

動手做

實作 Lab：試用 Guard：建第二個 policy、管外部帳號

約 30 分鐘Org admin；Atlassian Guard Standard（30 天免費試用）。SSO 與 SCIM 需要外部 IdP，Lab 只看畫面

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：開 Atlassian Guard 的 30 天試用，看 authentication policies、identity providers、external user policy、API token activity 的畫面，並對 external user 開一次 one-time passcode。

這個 Lab 對應的考點

多個 authentication policy、SAML SSO、user provisioning、external user policy 都屬於 Guard Standard；policy 成員來自 managed accounts；external user policy 一次套用到所有 external user。

準備

  • Leo 能用自己的瀏覽器設定檔登入 labjira（Leo 是 external user）。

步驟

  1. 你應該看到：試用開始；Security 底下的 User security 出現 Authentication policies、Identity providers、External users 等項目。
  2. 你應該看到：這是 default policy，有 Settings 與 Members 兩個分頁。Lab Org 沒有 managed account 時，Members 通常是空的。
  3. 你應該看到：清單出現第二個 policy。建立多個 policy 需要 Guard Standard，所以試用前做不到。
  4. 你應該看到：看得到可選的 identity provider（例如 Okta、Microsoft Entra ID、Google Workspace），以及之後要設定的 SAML single sign-on 與 user provisioning。
  5. 你應該看到：Policy 更新完成；這個設定套用到所有 external user，不能只套某幾個人。
  6. 你應該看到：通常會被要求輸入寄到 Leo email 的一次性密碼，驗證後才能看到 Jira 的內容。
  7. 你應該看到：API token activity 只列 managed account 建立的 token，Lab Org 通常是空的；Analytics 有使用者、驗證方式等圖表，部分圖表要 Guard 或 Premium 才顯示。

登、配、令、外、影SSO（登入）、provisioning（配發）、API token（令牌）、external user、shadow IT：Guard Standard 的五件事。
偵測分類找 PremiumThreat detection、sensitive data、data classification 是 Guard Premium。
Guard Standard、Guard Premium，誰要付費
  • Standard：SSO、SCIM、API token、多 policy；Premium：偵測、分類。
  • 每人只算一次；Enterprise 已含 Guard Standard。
依使用者分組設定登入規則
  • Default policy 自動收新的 managed account；建第二個 policy 要 Guard Standard。
  • 啟用 SSO 後，2SV 與密碼規則改在 IdP 設定。
把 identity provider 接到 organization
  • SAML SSO 只適用已驗證網域的帳號。
  • SCIM 同步的 group 是唯讀，只能在 IdP 改。
撤銷 user API token、管住外部帳號
  • Insights → API token activity：看、撤銷 managed account 的 token，撤銷不可復原。
  • External user policy：SSO、one-time passcode 或 None，套用全部 external user。
使用者自己開的 app、organization 的使用分析
  • Shadow IT＝使用者自己註冊的 app，不在 Apps 頁。
  • Insights → Analytics 看驗證方式、網域分布、使用率。
